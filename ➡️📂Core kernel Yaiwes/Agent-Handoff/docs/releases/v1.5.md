# Agent Handoff 1.5

Agent Handoff 1.5 keeps auxiliary work subordinate to the result that a work item was authorized to deliver.

## Why this change was needed

Standard 1.4 prevented unsupported security and evidence work from expanding scope, but the general workflow still treated any "stable stage" as reportable progress. A failed smoke wrapper, test harness, CI layer, evidence collector, release helper, or other supporting tool could therefore become its own repair stage, handoff, approval gate, and completion target.

That behavior can create repeated process loops while the primary outcome remains unchanged. Standard 1.5 closes this gap by defining outcome progress, keeping localized supporting fixes inside the original execution envelope, and limiting stages and handoffs to legitimate outcome boundaries.

## Highlights

- Every meaningful work claim records a `Primary outcome`, `Smallest acceptance proof`, and `Execution envelope`.
- The execution envelope records existing authorization; an agent cannot create authority by declaring a broader envelope.
- Supporting work stays minimum sufficient and subordinate to the primary outcome.
- A localized, reversible, in-scope supporting defect is normally fixed and verified inside the current work item and authorization.
- An unchanged rerun is a retry; a bounded rerun after an evidence-based fix is verification.
- Unless the execution envelope is stricter, one bounded verification rerun after each relevant fix is permitted.
- The fix-and-verification cycle stops when it would exceed the execution envelope, repeats the same failure without a new evidence-based fix, or triggers `progress-stalled`.
- A new owner decision is required only when an explicit outcome, scope, architecture, baseline, external-effect, resource, risk, security, or enforced permission boundary is crossed.
- A supporting-tool failure alone does not create a stage, handoff, completion target, or approval requirement.
- Two consecutive supporting-only updates without outcome progress trigger `progress-stalled` and a shortest-path replan.

## Retry and verification

| Action | Meaning | Default handling |
|---|---|---|
| Repeat the same failed action without a relevant change | Retry | Avoid unless a reason is documented |
| Rerun the affected check after an evidence-based fix | Verification | Keep inside the current work item and execution envelope |

## Legitimate stage and handoff boundaries

A stage result or handoff is appropriate only when:

- the primary outcome materially advanced;
- the smallest acceptance proof completed;
- a verified blocker remains outside the current execution envelope; or
- work is genuinely interrupted or transferred.

Routine supporting fixes and their verification belong in the next legitimate stage or final report.

## What this does not require

Standard 1.5 does not require automated semantic scoring of progress, a fixed supporting-work percentage, a new Issue for each auxiliary failure, or removal of project-specific approval gates.

It does not override tool, platform, repository, or organization permissions. It preserves the existing security baseline, proportional-security rule, containerization decision gate, GUI-testing rule, and human control of destructive, external, architectural, or materially resource-expanding actions.
