# Agent Handoff 1.4

Agent Handoff 1.4 prevents security and evidence work from blocking acceptance or expanding scope unless a current-scope risk is verified as High or Critical, so unsupported hardening cannot delay a working vertical slice.

## Highlights

- Security work may block acceptance or expand scope only for a verified High or Critical current-scope risk.
- Verification requires reproducible evidence from the current implementation or environment, or a directly applicable authoritative source.
- A suspected High or Critical risk permits only a short, time-boxed investigation until confirmed.
- Low, Medium, unrated, and unverified risks remain non-blocking warnings, documentation, backlog, owner-accepted risk, or out of scope.
- MVPs, prototypes, and runtime spikes preserve the existing security baseline, address verified High or Critical risks, and run the smallest useful end-to-end scenario early.
- Optional hardening, exhaustive compatibility checks, and defense in depth follow a working vertical slice.
- An exact acceptance criterion or verified legal or project requirement may independently block acceptance only when cited.
- Secrets, untrusted input, external network access, privilege boundaries, destructive actions, sensitive data, and supply-chain exposure justify checking applicability but do not by themselves prove severity.
- Existing security controls cannot be weakened without an explicit owner decision.
- A 10–15% security-and-evidence share is only a non-binding planning heuristic.
- Reviews, reports, and handoffs distinguish verified blockers, time-boxed investigations, follow-up hardening, and owner-accepted risk.

## What this does not require

Standard 1.4 does not require a threat model for every Pull Request, automated risk scoring, a fixed security-work percentage, new approval stages, or a separate Issue for Low, Medium, unrated, unverified, or optional hardening.

The checker verifies the presence of one proportionality checklist item. It does not determine whether a threat is realistic or whether a control is sufficient.

## Compatibility

Standard 1.4 preserves the containerization decision gate, stable GUI testing rules, task reporting, work claims, and the existing security baseline from Standard 1.3.

Projects can adopt the proportionality rule without changing application architecture or removing existing controls.
