# Agent Handoff 1.5.1

Agent Handoff 1.5.1 makes blocking Pull Request reviews actionable for coding agents without locking them to one reviewer-proposed implementation.

## Why this change was needed

Standard 1.5 defines outcome progress, execution envelopes, approval boundaries, and when findings may block acceptance. It did not define the reviewer-to-agent handoff after a blocking defect was found.

A bare defect statement can force another agent to reconstruct the reproduction, violated contract, invariants, scope, and expected proof from chat history. At the other extreme, treating the reviewer's implementation suggestion as the only valid fix can create a hidden acceptance criterion and reject equally safe solutions.

Standard 1.5.1 closes both gaps with a proportionate correction contract.

## Highlights

- New `ai/REVIEW_PROTOCOL.md`.
- Findings are classified `blocking`, `non-blocking`, or `question`.
- Every blocking finding has a stable ID such as `RH-01`.
- Evidence and reproduction identify the location, trigger, event order when material, observed result, and expected result.
- The violated behavioral, architectural, compatibility, security, or acceptance contract is explicit.
- Cause confidence is marked `confirmed`, `likely`, or `unknown`.
- Required outcomes, preserved invariants, scope guards, applicable verification, and acceptance criteria travel with the finding.
- Implementation guidance is optional and non-binding when an equivalent safe correction satisfies the contract.
- Tests are selected by applicability; race tests are reserved for concurrency and lifecycle-ordering scenarios.
- One correction report maps every blocking finding ID to the change and evidence.
- Finding state follows `open -> addressed -> verified` independently of Pull Request labels.
- Agent-reported `addressed` status does not automatically resolve a thread or replace reviewer verification.

## Blocking correction contract

```text
Finding ID
Evidence and reproduction
Violated contract
Cause: confirmed | likely | unknown
Required outcome
Invariants and scope guard
Implementation guidance (optional)
Verification
Acceptance criteria
```

The complete contract is mandatory only for blocking findings. Non-blocking suggestions and questions may remain concise but must be classified clearly.

## Implementation freedom

The required outcome, invariants, applicable mandatory requirements, and acceptance criteria are normative.

A reviewer may recommend an implementation. Another approach remains valid when it achieves the required outcome, preserves the stated invariants, remains inside the execution envelope, and provides the required evidence. The reviewer cannot reject it solely for differing from optional guidance.

A review finding does not widen authority or Issue scope. When every safe correction crosses an existing approval boundary, the agent stops and requests the applicable owner decision.

## What this does not require

Standard 1.5.1 does not require a long template for nits, automated semantic scoring of review quality, every test category for every finding, a repository file for every review, or a new Issue for each correction cycle.

It preserves the outcome-oriented execution rule, proportional-security threshold, existing security baseline, containerization decision gate, GUI-testing rule, and external permission systems.
